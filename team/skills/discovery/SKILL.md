# Product discovery

Start with an example, not a feature list. Read the request and current
behavior, then reconstruct a specific person's first useful outcome:
trigger, available information, decisions, failure, recovery, and result.
For a bug, ask for the smallest input that distinguishes observed from
expected behavior. For new work, establish which audience and first task
the delivery must serve, and what can wait.

| If the unknown is about | Find out |
| --- | --- |
| Audience or workflow | Who acts, how often, on what device, with what consequences? |
| Scope or success | What changes in the critical journey? Which path may stay as is? |
| Direction or delivery | What changes in brand, accessibility, data, cost, rollout, or ongoing operations? |
| Existing behavior | What does the committed seed actually do? Can we reproduce the mismatch? |

Gather specialist sketches or feasibility evidence before asking the user to
choose. Ask only the few decisions that can change direction or complexity
at each round. State a recommendation with consequences and mark facts,
user decisions, delegated defaults, and open items separately. Do not
present untested proposals as requirements.

Replace “make filters work” with “with active and archived records present,
selecting Archived shows only archived records; clearing the filter returns
both sets without resetting the search query.” Have QA tie this claim to
an independent check. Present the approved-scope proposal, exclusions,
dependencies, required evidence, and review digest as one packet.
